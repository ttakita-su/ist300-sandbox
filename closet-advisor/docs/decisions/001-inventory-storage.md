**Context:** D08 needs a personal closet inventory. A person adds an item with a name, category (clothing, sneakers or watches), brand and color, sees it, edits it and deletes it, and it has to survive a page reload. There are no accounts or backend in this step. The assignment suggested localStorage "if appropriate". Rotation already keeps owned items in IndexedDB: database `rotation-prototype` version 2, store `ownedItems` keyed by `id` with a `userId` index. That database sits behind the in-tab API (`js/server/db.js`), with a memory fallback when the browser blocks storage. The same database holds photos as Blobs and outfits that point at item ids, and export and account deletion read it too. localStorage holds only the session token (`rotation.session.v1`) and the theme (`rotation.theme`).

**Decision:** Keep the inventory in the existing IndexedDB `ownedItems` store. It is reached through `createOwned`, `listOwned` / `getOwned`, `updateOwned` and `deleteOwned` (`js/server/ops/inventory.js`). D08 adds no new store, index or storage layer, so `DB_VERSION` stays at 2 and existing data is untouched.

**Why not the alternative:** A localStorage inventory would be a second copy of the same items. Outfits, export, account deletion, duplicate warnings and stylist shares would keep reading IndexedDB while the D08 screens read localStorage, and the two would disagree after the first edit. localStorage also has three limits here: it stores only strings, so it can't hold photo Blobs; it is synchronous on the page's main thread; and it is capped at about 5 MB per site, which a closet with photos passes quickly. Switching over would also need a data migration for a feature that already works.

**What it costs:** Items still live in one browser on one device. Clearing site data or using a private window loses them, and when IndexedDB is blocked the memory fallback keeps nothing after the tab closes. IndexedDB is asynchronous and harder to look at by hand than localStorage: in DevTools it is under Application → IndexedDB. Two tabs share the store with no version check, so when both change the same field the last save wins (D08 break test U2). The ownership check runs inside the browser tab, so it isn't a security boundary.

**What would change my mind:** Accounts that follow a person across devices (D10) or a real backend. Then items move to the server database planned in `docs/PLAN.md` and `supabase/migrations/`, with IndexedDB at most as an offline cache. A much smaller app, with no photos and no other features reading the items, would make localStorage the simpler choice.
